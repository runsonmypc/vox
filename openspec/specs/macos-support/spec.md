## Purpose

Enables vox to operate natively on macOS Darwin, providing voice-to-text dictation with active application context, screen vocabulary extraction, audio attenuation, and seamless background execution.

## Requirements

### Requirement: Cross-Platform Single-Instance Locking
The daemon SHALL ensure that only one instance runs per user at a time by holding an advisory lock on its own per-user lock directory: `$XDG_RUNTIME_DIR/vox` on Linux (or `/run/user/<uid>/vox` when the variable is unset), otherwise `~/.local/state/vox`, created with mode 0700. The lock SHALL be on the directory itself, so deleting files cannot admit a second instance, and SHALL work on macOS and Linux without Linux-only abstract Unix domain sockets.

#### Scenario: First instance starts successfully
- **WHEN** no other vox instance is running for this user
- **THEN** the daemon acquires the lock and proceeds with initialization

#### Scenario: Second instance is prevented from starting
- **WHEN** a vox instance is already active and running for this user
- **THEN** a newly launched instance fails to acquire the lock, logs at INFO that Vox is already running, and exits successfully (code 0) before loading its configuration or prompting for permissions, so launchd and systemd do not restart it

#### Scenario: Other users
- **WHEN** another account on the same machine is running Vox
- **THEN** this user's Vox still starts, because each user has their own lock directory

#### Scenario: Lock cannot be created
- **WHEN** the lock directory cannot be created or opened
- **THEN** Vox logs an error naming the directory and exits with code 78, which the Linux login service does not restart

### Requirement: macOS Active Application and Window Detection
On macOS, the daemon SHALL determine the frontmost application, its bundle identifier, its process ID, its focused window and that window's title using native macOS APIs instead of X11 utilities (`xdotool`, `xprop`). Detection SHALL be safe to run from a worker thread.

#### Scenario: Active app is classified correctly
- **WHEN** recording is initiated while a known terminal, editor, chat, browser, or email client is focused on macOS
- **THEN** the daemon resolves the application bundle identifier and maps it to the appropriate `AppType` (e.g., `TERMINAL`, `EDITOR`, `CHAT`, `BROWSER`, `EMAIL`)

#### Scenario: Window title fallback when unavailable
- **WHEN** an application window title cannot be inspected due to privacy restrictions or absence of a window
- **THEN** the daemon reads the focused window's title through the Accessibility API, falls back to the application's localized name, runs no AppleScript, and raises no unhandled exception

#### Scenario: Focused window identified
- **WHEN** the frontmost application has an on-screen normal window
- **THEN** the daemon records the window ID (CGWindowID) of the application's frontmost normal window, which is its focused window

### Requirement: macOS Text Injection and Clipboard Handling
On macOS, the daemon SHALL insert transcribed text at the cursor position by writing it to the system pasteboard through native pasteboard APIs, posting a Command+V (`⌘V`) key combination to the active application, and then restoring the user's previous pasteboard contents. The key posted SHALL be the one that types "v" in the current keyboard layout, and pasting SHALL be safe to run from a worker thread.

#### Scenario: Text injection into GUI application
- **WHEN** transcription completes for a focused GUI application (editor, browser, chat)
- **THEN** the daemon saves every item on the pasteboard with the data of every type it offers, writes the transcript and its transient markers (`org.nspasteboard.TransientType` and `org.nspasteboard.AutoGeneratedType`, set before the text) as one pasteboard item in a single write kept to this Mac, posts Command+V, waits for the target to read it, and then writes every saved item back

#### Scenario: Pasteboard refuses the dictation
- **WHEN** the pasteboard will not take the dictation
- **THEN** the paste fails before Command+V is sent, so the old clipboard is never pasted in its place

#### Scenario: Password manager's copy
- **WHEN** the saved clipboard carries `org.nspasteboard.ConcealedType`, as a password manager marks a copied password
- **THEN** the daemon writes it back for this Mac only, so Universal Clipboard does not offer it to the user's other devices, while any other clipboard is written back as an ordinary copy

#### Scenario: Text injection into terminal application
- **WHEN** transcription completes for a focused macOS terminal application (Ghostty, iTerm2, Terminal.app)
- **THEN** the daemon simulates Command+V (`⌘V`) rather than Linux-style Control+Shift+V

#### Scenario: Keyboard layout without V in the usual place
- **WHEN** the current layout is Dvorak or another layout that moves "v", or a layout with no Latin "v" such as Russian
- **THEN** the daemon posts Command with the key that types "v" in that layout, or with the ANSI V key when the layout has no "v", which is what macOS itself does for Command shortcuts

#### Scenario: Pasteboard refuses the saved contents
- **WHEN** the pasteboard will not take the saved items back
- **THEN** the daemon restores at least their plain text, or leaves the clipboard empty, and logs a warning; plain text from a concealed clipboard gets the `org.nspasteboard.ConcealedType` marker back, set before the text and kept to this Mac

### Requirement: macOS Audio Volume Attenuation
When attenuation is enabled on macOS, the daemon SHALL query the current output volume and attenuate system output volume while recording, restoring the original volume level upon completion, cancellation, error or exit, including an exit on SIGTERM.

#### Scenario: Volume attenuated during recording
- **WHEN** audio recording starts with attenuation enabled
- **THEN** the current macOS system volume is saved and output volume is reduced to the configured attenuation level

#### Scenario: Volume restored when recording stops
- **WHEN** audio recording stops, is cancelled, hits an unexpected error, or Vox quits mid-recording (from the tray, with Ctrl-C, or on SIGTERM from a service stop, a logout or an update), even while the volume is still being lowered
- **THEN** the system volume is restored to its original pre-recording level

#### Scenario: Second SIGTERM
- **WHEN** a second SIGTERM arrives while Vox is shutting down
- **THEN** Vox ends at once

### Requirement: macOS Screen Context Capture
On macOS, while `[context] screen` is on, the daemon SHALL capture text from the focused window only, never the whole display or the application's other windows, for vocabulary and technical term extraction, using native window capture and on-device text recognition.

#### Scenario: Neural OCR extracts vocabulary hints
- **WHEN** screen hints are on and a batch or whisper.cpp recording begins, or a streaming recording falls back to batch
- **THEN** only the focused window (the frontmost application's frontmost normal window, by its CGWindowID) is captured to a temporary file, recognized with Apple Vision text recognition with language correction off, and the file is deleted; the recognized lines are kept one per line, so the secret filter's end-of-line rule stops at the line, and the words, minus secret-looking tokens, are added to the transcription hints

#### Scenario: No focused window known
- **WHEN** no window ID is known for the focused application
- **THEN** nothing is captured, and the daemon never falls back to capturing the whole screen

#### Scenario: Terminal tmux pane extraction
- **WHEN** the active application is a terminal, exactly one tmux client runs under the terminal's process tree, and every other process in that tree with a controlling terminal is on that client's tty (the app has no other window or tab session)
- **THEN** the daemon captures that client's visible pane text for context hints before trying window OCR; otherwise (no client, several clients, or another window or tab of the same app) it reads no tmux pane and recognizes the focused window with Apple Vision, and it never reads a tmux session that is not attached inside the focused terminal

#### Scenario: Screen context off
- **WHEN** `[context] screen = false`
- **THEN** no capture runs and no window-title or screen words are sent, so macOS never asks for the Screen Recording permission

### Requirement: macOS System Permissions Diagnostics
On macOS, the daemon SHALL check the Accessibility permission at startup and give actionable instructions when it is missing, and SHALL detect a denied microphone from the audio it records.

#### Scenario: Accessibility permission missing
- **WHEN** vox starts on macOS without Accessibility permissions granted to the host process
- **THEN** the daemon logs a prominent warning directing the user to enable Accessibility in System Settings, and the tray's status line shows "Accessibility access needed" (checked without prompting again)

#### Scenario: Microphone denied
- **WHEN** a recording's samples are all exactly zero, which is what macOS delivers to a process without Microphone access
- **THEN** it is not transcribed, the daemon logs a warning pointing to System Settings > Privacy & Security > Microphone, the error sound plays, and the tray shows "Microphone is silent: check its permission" until a recording with real audio

### Requirement: macOS Background Daemon LaunchAgent
The project SHALL provide a macOS LaunchAgent property list template that `install.sh` renders with absolute paths, allowing vox to be started, stopped, and managed via `launchctl` as a persistent background daemon for the user session. Its output SHALL go to a log file only the user can read.

#### Scenario: Daemon starts via launchd
- **WHEN** the LaunchAgent is loaded via `launchctl bootstrap` or `launchctl load`
- **THEN** the vox daemon starts in the background and restarts automatically after a crash, but not after Quit or when another instance is already running, which exit successfully

#### Scenario: Rendered agent
- **WHEN** `install.sh` installs the LaunchAgent
- **THEN** the agent runs `~/.local/bin/vox` by its absolute path, with a PATH that includes `~/.local/bin`, `/opt/homebrew/bin` and `/usr/local/bin`, and a umask of 077

#### Scenario: Shown as Vox Transfer in Login Items
- **WHEN** `install.sh` installs the LaunchAgent
- **THEN** the agent names the launcher's bundle id, `com.runsonmypc.vox.launcher`, in `AssociatedBundleIdentifiers`, so System Settings lists it under Login Items as the launcher app, Vox Transfer, while its label stays `com.runsonmypc.vox`

#### Scenario: Private log file
- **WHEN** the LaunchAgent runs Vox
- **THEN** its output goes to `~/Library/Logs/Vox/vox.log` (directory 0700, file 0600), and the installer deletes the old `/tmp/vox.stdout.log` and `/tmp/vox.stderr.log` files the user owns

#### Scenario: Log kept small
- **WHEN** Vox starts with its output going to a regular log file larger than 10 MiB
- **THEN** it empties the file and logs one INFO line saying so, while output that is not a regular file, such as the Linux journal, is left alone
